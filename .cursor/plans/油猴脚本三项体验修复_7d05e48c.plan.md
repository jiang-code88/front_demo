# 油猴脚本三项体验修复

针对 [tampermonkey-sql-highlight.user.js](tampermonkey-sql-highlight.user.js) 当前实现（已完成"多 Tab 独立查询"重构，见 [sql编辑器多tab独立查询重构_a52ec6a0.plan.md](.cursor/plans/sql编辑器多tab独立查询重构_a52ec6a0.plan.md)），修复用户反馈的三个问题。之前的重构**主动删除了** Tab 数据的 GM 持久化（认为没必要），这次按用户反馈把"内容持久化"重新加回来，但保持轻量。

## 问题 1：刷新页面后所有 Tab 的 SQL 内容丢失

**方案**：新增一个轻量的 GM 存储键，只持久化"输入状态"（SQL 文本 / 所选数据库 / Tab 名称），**不持久化查询结果**（已与用户确认：结果留空，刷新后需要重新点提交才能看到，避免展示过期数据、也省去大结果集的存储成本）。

- 新增 `STORAGE_KEY_TABS = 'sql_hl_tabs_v1'`。
- 新增 `serializeTabsSnapshot()`：把 `tabs` 数组精简为 `{ id, name, customName, content, dbName, databaseSuffix, currentErp }`（不含 `resultHtml`/`status`/`page`/`errorMsg`/`requestSeq`/`abortController`），连同 `activeTabId`、`nextTabId` 一起打包。
- 新增 `persistTabsNow()`（立即持久化）与 `persistTabsDebounced()`（防抖 ~400ms 包一层，减少打字时的写入频率），内部都是 `GM_setValue(STORAGE_KEY_TABS, JSON.stringify(snapshot))`。
- **触发时机**：
  - CM6 `updateListener` 里 `update.docChanged` 分支（[1328-1336 行](tampermonkey-sql-highlight.user.js)）：先把 `getActiveTab().content` 同步为最新文档内容，再调用 `persistTabsDebounced()`（目前只有 `syncToTextarea()`，`tab.content` 只在切换 Tab 时才更新，必须改成随打字实时更新才能保证持久化数据不滞后）。
  - `switchTab()` / `addTab()` / `closeTab()` / 重命名提交（`startRenameTab` 的 `commit()`）/ `#db_name` 的 `change` 监听里：调用 `persistTabsNow()`（这些都是低频操作，不需要防抖）。
  - 新增 `window.addEventListener('beforeunload', ...)`：调用 `saveCurrentTabState()` + `persistTabsNow()`，确保刷新前最后一次按键也能被防抖之外兜底保存。
- **加载时机**：改造 `restoreTabs(initialResult)`（[770-790 行](tampermonkey-sql-highlight.user.js)）：
  - 先尝试 `GM_getValue(STORAGE_KEY_TABS)`，`JSON.parse` 并校验形状（`tabs` 是非空数组）。
  - 校验通过：用保存的每个 tab 数据通过 `createTabData(t.id, t.content)` 重建，再覆盖 `name`/`customName`/`dbName`/`databaseSuffix`/`currentErp`；`nextTabId` 取 `max(保存值, 所有 id+1)`；`activeTabId` 取保存值（若已不在恢复的 tab 列表里则回退到第一个）。此时忽略 `initialResult`（已知边缘场景：刷新前一刻恰好是服务端整页渲染结果页时会被忽略，影响极小，不专门处理）。
  - 校验失败/无数据：保持现有兜底逻辑（用当前 textarea 内容 + 当前 `#db_name` + `initialResult` 创建 Tab 1）。
- 额外加一个 `GM_registerMenuCommand('SQL 高亮：清除已保存的 Tab 数据', ...)`（配套 `@grant GM_deleteValue`），方便存储数据损坏/想清空重来时手动重置，不强制。

## 问题 2：提交前校验是否已选择数据库

**方案**（已与用户确认：不用 `alert()` 弹窗，改成内嵌红色提示 + 高亮下拉框，不打断操作）。

- 在 `submitQuery(tab, opts)`（[1077 行起](tampermonkey-sql-highlight.user.js)）里，`saveCurrentTabState()` 同步之后、真正发起 `fetch` 之前插入校验：`if (!tab.dbName) { showDbRequiredHint(); return; }`——这一处守卫同时覆盖"点击提交"和"分页/跳转页"两条调用路径，不需要在多处重复判断。
- 新增 `showDbRequiredHint()`：
  - 给 `#db_name` 加一个临时 CSS 类（如 `cm-db-highlight`，红色描边），`setTimeout` 约 1.5s 后自动移除，并 `focus()` 该下拉框。
  - 直接在 `resultPanelEl` 的 `.cm-result-content` 里写入一段醒目提示（复用已有的 `.cm-result-warn` 样式）：“请先选择要查询的数据库”。
  - 不改变 `tab.status`/`tab.resultHtml`（这只是一次性的操作反馈，不是查询状态，避免污染持久化模型或误导后续渲染）。
- CSS 新增 `.cm-db-highlight { outline: 2px solid #e06c75; border-radius: 3px; }`。

## 问题 3：长查询可取消 / 可不等待直接重写重提

**根因**：现在提交期间 `setSubmitButtonBusy(true)`（[1051-1063 行](tampermonkey-sql-highlight.user.js)）会把提交按钮 `disabled = true`，用户虽然能编辑 SQL，但点不动提交按钮，只能死等当前请求结束。

**方案**：把"提交"按钮在查询期间变成可点击的"取消查询"按钮，点击即可中止等待，之后可立即改 SQL 重新提交。

- `createTabData()`（[579-597 行](tampermonkey-sql-highlight.user.js)）新增字段 `abortController: null`。
- `submitQuery()` 里创建 `var controller = new AbortController(); tab.abortController = controller;`，`doFetch` 调用时传入 `signal: controller.signal`；请求结束（成功/失败任一分支之后的收尾 `.then`）里把 `tab.abortController = null`。
- 新增 `cancelQuery(tab)`：
  - 仅当 `tab.status === 'loading'` 时生效；`tab.abortController && tab.abortController.abort()` 后清空引用；
  - `tab.requestSeq++`（让原请求即使之后 resolve/reject 也会因序号不匹配被现有逻辑丢弃，不需要单独处理 `AbortError`）；
  - `tab.status = 'cancelled'`；若是当前激活 Tab，`renderResultPanel(tab)` + `setSubmitButtonBusy(false)`。
- `renderResultPanel()`（[1014-1046 行](tampermonkey-sql-highlight.user.js)）新增 `case 'cancelled'`：显示"已取消查询，可修改 SQL 后重新提交"占位文案。
- `setSubmitButtonBusy(busy)` 改为**不再 disable 按钮**，只切换文案（`"取消查询"` / 还原原文案）和一个视觉样式类（如 `cm-btn-busy`，橙色底色提示这是取消态）。
- 提交按钮的 click 绑定（[1359-1369 行](tampermonkey-sql-highlight.user.js)）改为二态分支：

```javascript
submitBtn.addEventListener('click', function (e) {
  e.preventDefault();
  e.stopPropagation();
  var tab = getActiveTab();
  if (!tab) return;
  if (tab.status === 'loading') {
    cancelQuery(tab);
  } else {
    submitQuery(tab, { page: 1 });
  }
}, true);
```

  这样 `Ctrl+Enter`（内部就是 `btn.click()`）在查询期间也自动变成"取消"，行为一致。
- `loadTabState(tab)`（[712-764 行](tampermonkey-sql-highlight.user.js)）在 `renderResultPanel(tab)` 之后补一行 `setSubmitButtonBusy(tab.status === 'loading')`——修复一个隐藏的现有小问题：目前切换 Tab 时按钮的"查询中"文案/禁用状态不会跟着目标 Tab 的真实状态刷新（比如从一个正在查询的 Tab 切到空闲 Tab，按钮还残留着"查询中"）。
- 分页事件委托（`createResultPanel` 内的 `click`/`keypress` 处理，[974-1009 行](tampermonkey-sql-highlight.user.js)）里各加一行 `if (tab.status === 'loading') return;`，避免在当前请求还没结束/取消时误触发重复分页请求。

**已知限制（不专门处理）**：取消只是让前端不再等待这次响应，后端此时是否真的中止了 SQL 执行不受我们控制（没有可用的服务端 kill-query 接口）；这符合用户描述的"主动不再等待"这个诉求，但不等同于"服务端立刻停止执行"。
